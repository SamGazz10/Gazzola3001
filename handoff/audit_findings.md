## Brief items 1 (Engineering problem) and 2 (Inputs and outputs); rubric row "Engineering problem, inputs and outputs"

**Auditor's summary.** Sections 1-2 are concise and mostly accurate. The input table matches features.py exactly: names, vocabularies, the 24 circuits plus generic, NUMERIC_RANGES and training ranges. The headline numbers (2.0/3.8/15.7 points, 47 % vs 44 %, under 1 % without Boost) and the README CLI output reproduce exactly. They fall short of Excellent for five reasons. The mechanical-engineering framing is never stated. One rationale (rule-parameter sensitivity) has no supporting work. Several inputs have no operational meaning, and the table has no defaults. The output claims calibration without saying it is only against the simulator. Most seriously, running the code shows four places where the documented input handling does not match what the code does: API/CLI defaults differ, a pandas Series is silently ignored, NaN is silently replaced, and the training-range warning misses the segment- and condition-specific ranges the table lists.

### [A1] (must) overtake/predict.py:151-162 (complete) vs overtake/predict.py:197-201 (scenario_from_args); docs/project_documentation.md Section 2 'Invalid, missing...' row 2 (line 121); README.md:91

*[Status: FIXED on report-polish: situational defaults shared via features.situational_defaults/predict.complete]*

**Issue.** The Python API and the CLI use different defaults. The CLI sets run_length_m to 150 m for corner segments and track_temp_c to 20 C for damp/wet. The Python API always uses DEFAULTS (800 m, 35 C). So a default corner attack from Python is an 800 m run, far outside the corner training range of 50-300 m, and no warning is given. The doc says omitted fields take 'Default value from features.DEFAULTS', which is false for the CLI.

**Evidence.** Python: p.predict({'segment':'slow_corner'}) -> 0.527, p.out_of_range(...) -> []. Python with run_length_m=150 -> 0.040. CLI: `python -m overtake.predict --gap 1.0 --segment slow_corner` -> 'P(overtake) = 4.0%'. The same nominal 'default' scenario gives 52.7 % from one interface and 4.0 % from the other.

**Proposed fix.** Move the conditional defaults into complete() so both interfaces share them. After the DEFAULTS loop: `if 'run_length_m' not given: df['run_length_m'] = np.where(df['segment']=='straight', 800.0, 150.0)`; `if 'track_temp_c' not given: df['track_temp_c'] = np.where(df['track_condition']=='dry', 35.0, 20.0)`. Then drop the duplicate logic in scenario_from_args. Add a test: predict({'segment':'slow_corner'}) equals predict({'segment':'slow_corner','run_length_m':150}). Doc row 2 wording: 'Default value from features.DEFAULTS, except run_length_m (800 m on a straight, 150 m into a corner) and track_temp_c (35 C dry, 20 C damp/wet); overtake_mode defaults to gap_s <= 1'.

### [A2] (must) overtake/features.py:293-299 (as_frame); overtake/predict.py:101-124; docs/project_documentation.md:90

*[Status: FIXED on report-polish: as_frame and predict accept pandas Series]*

**Issue.** Section 2 says a scenario can be 'a pandas DataFrame row'. Passing one (a pd.Series) silently ignores every value the user set. as_frame turns the Series into a 19-row, one-column frame, complete() fills every feature with its default, and predict returns 19 copies of the default probability with no error.

**Evidence.** s = pd.Series({**DEFAULTS, 'gap_s': 0.3, 'track_condition': 'wet'}); p.predict(s.to_dict()) -> 0.569, but p.predict(s) -> array of shape (19,), all 0.43977505 (the default scenario). as_frame(s).head() shows a single column '0' holding 'wet', 'straight', 'generic', ...

**Proposed fix.** In as_frame add `if isinstance(scenarios, pd.Series): scenarios = [scenarios.to_dict()]` before the dict branch. In predict return a float for a Series as well as a dict: `isinstance(scenarios, (dict, pd.Series))`. Add a test that predict(df.iloc[0]) == predict(df.iloc[0].to_dict()).

### [A3] (must) overtake/predict.py:156 (fillna) and 158-161; CLI main(); docs Section 2 row 2

*[Status: FIXED on report-polish: None only means default; NaN rejected by validate; CLI uses finite_float]*

**Issue.** NaN in a numeric field is silently treated as 'omitted' and replaced by the default, while Overtake Mode is computed from the NaN gap as off. On the CLI, `--gap nan` (argparse float accepts it) exits 0 and prints a probability for an inconsistent scenario (gap 1.0 s, Overtake Mode off) while showing 'Gap: nan s'. Section 2 says non-numeric/missing numbers raise ValueError and the CLI exits 2.

**Evidence.** `python -m overtake.predict --gap nan` -> 'Overtake Mode off ... Gap: nan s ... P(overtake) = 20.0%', exit=0. Python: p.predict({'gap_s': float('nan')}) -> 0.4398, identical to the default.

**Proposed fix.** Fill defaults only for keys that are absent or exactly None, not NaN. For dict input, substitute before building the frame: `{k: (DEFAULTS[k] if v is None else v)}`. Let validate() reject NaN ('gap_s: missing or not a number'). In the CLI, reject non-finite floats with a custom argparse type: `def finite(x): v=float(x); if not math.isfinite(v): raise argparse.ArgumentTypeError('must be a finite number'); return v`. Doc row 2: 'Field omitted or None (not NaN) when predicting'.

### [A4] (must) overtake/predict.py:126-148 (out_of_range); docs/project_documentation.md:99,102 and row 3 of the handling table (line 122)

*[Status: FIXED on report-polish: out_of_range checks per-segment/condition ranges and Overtake Mode vs gap]*

**Issue.** The input table gives conditional training ranges ('250-1300 (straights), 50-300 (corners)'; '18-55 dry, 10-32 wet') and says inputs outside the training range get a warning. out_of_range only compares each input with its overall min-max (run 50-1300 m, temp 10-55 C), so these conditional extrapolations go unflagged. It also ignores combinations never seen in training (Overtake Mode on at a 2.5 s gap; training uses detection gap = gap + N(0, 0.2)).

**Evidence.** out_of_range({'run_length_m':100,'segment':'straight'}) -> []; out_of_range({'run_length_m':1000,'segment':'slow_corner'}) -> []; out_of_range({'track_condition':'wet','track_temp_c':50}) -> []; p.predict({'overtake_mode':True,'gap_s':2.5}) accepted with no warning. Preprocessor mins/maxs: run_length_m 50.0-1300.0, track_temp_c 10.0-55.0.

**Proposed fix.** Add conditional checks to out_of_range: run_length_m against 250-1300 if segment=='straight' else 50-300; track_temp_c against 18-55 if dry else 10-32; warn if overtake_mode is on and gap_s > 1.6, or off and gap_s < 0.4 (beyond 3 sd of the detection noise). Ideally store these per-group ranges in the Preprocessor at fit time rather than hard-coding them. If not fixed in code, change doc line 122 to: 'Accepted; out_of_range warns when a numeric input is outside its overall training min-max (not the per-segment or per-condition ranges in the table above)'.

### [A2] (must) docs/project_documentation.md:192-197 (Section 3.3, RK4 time integration)

*[Status: FIXED in new report and new `stability` experiment]*

**Issue.** The stability justification names the wrong fastest time scale. The battery ramp in physics.acceleration (MGU-K power ramped to zero over the last energy_smoothing_j = 20 kJ) gives de/dt a linear decay with eigenvalue -deploy*P_max/20 kJ = -17.5 1/s with Boost (tau = 57 ms, about the size of dt). RK4's real-axis stability limit |lambda*dt| <= 2.785 therefore gives dt < 0.16 s. Even the drag-plus-taper time scale at 306 km/h is about 2 s, not 8 s. The presentation brief asks explicitly 'How did you ensure numerical stability?', and the current answer is wrong.

**Evidence.** Numerical Jacobian (my check, read-only): d(P_ers)/de = -17.5 1/s with 10 kJ left; d(accel)/dv = -0.34 1/s at 60 m/s and -0.51 1/s at 85 m/s. On the 2,000 timestep-study scenarios (seed 7) against the dt=0.001 reference: scenarios where a battery runs out have max deficit error 2.65e-4 s at dt=0.1 and 8.0e-3 s at dt=0.15 (30x jump); all other scenarios go 1.66e-4 -> 3.18e-4 (1.9x). Battery overdraw (energy used minus energy available): 0 at dt<=0.1, 6.25 kJ at dt=0.15, 15.0 kJ at dt=0.2. This explains the unexplained 70x error jump between dt=0.1 and 0.2 in timestep.json.

**Proposed fix.** Replace 'the fastest physical time scale is the drag response, m/(rho CdA v) ≈ 8 s at 80 m/s, so an explicit method is stable for any step small enough to be accurate' with: 'The system is not stiff, but its fastest time scale is not the drag response (about 2 s near top speed): it is the 20 kJ ramp that switches the MGU-K off as the battery empties, tau = 20 kJ / 350 kW = 57 ms (eigenvalue -17.5 s^-1). RK4 is stable on the real axis for |lambda dt| < 2.785, i.e. dt < 0.16 s. At dt = 0.15-0.2 s the time-step study shows the error jumping 30x for scenarios whose battery runs out, and the battery being overdrawn by up to 15 kJ. dt = 0.05 s is a factor of 3.2 inside the limit.' Add the 20 kJ ramp to the parameter table (see A3) and a known-limitation line: 'reducing energy_smoothing_j below about 7 kJ would make dt = 0.05 s unstable'.
